# 3D 电梯控制模型 · 最优方案（三个 agent 讨论后的结论）

> **背景**：这是"3D 电梯控制模型"这一版最终采用的做法。
> 本机上有三个 agent（三个不同模型）各自独立出了一版方案，本文是**把它们摆在一起比、然后拍板**的结果。
> 比完之后**方案已经按结论落地**（不是纸面计划），落地状态见 §4。

---

## 0. 先说清楚："3D 电梯控制模型"到底指什么

这个说法至少有四种理解，方向完全不同。三个 agent **独立地都判成了同一种**，这一点很关键：

| 代号 | 理解 | 现场能不能讲 | 现在的状态 |
|---|---|---|---|
| **A** | **可交互的网页 3D 模型**（浏览器里能转、能点、能看整条控制链跑完） | ★★★ 一条链讲完 | **已存在，本次把它做成了主角** |
| B | 能 3D 打印的实物模型（机械件_演示样机） | ★★ 只能讲"机构" | 已做（8 个 STL + 9 张渲染图 + 校验报告）→ 当**加分实物** |
| C | 给 PPT / 视频用的 3D 渲染图与动画 | ★★ 是素材，不是模型 | 已做（9 张渲染图）→ 当**素材** |
| D | App 里的 3D / 2.5D 井道视图 | ★ 手机屏太小 | 已做（`ElevatorView.kt`）→ 当**真机证据** |

**结论：要的是 A。** 理由是三条独立的判断撞到了一起：

1. **只有 A 能讲"控制链"**。对方要看的不是"电梯会转"，而是"点一下之后发生了什么"。
   3D 打印件（B）只有一层机构、讲不了"轿厢在 2F/3F 之间跑"；App（D）在台上屏幕太小；
   C 是 A 的副产品。**只有 A 能把 App→BLE→ESP32→舵机→按钮→轿厢 串成一个画面。**
2. **A 已经存在、只差"讲清楚"**。`preview/elevator_3d_preview.html` 是一个 14 KB 的手写 Canvas 3D 井道，
   几何常量与安卓端 `ElevatorView.kt`、规格页 `SHAFT_MODEL.md` **逐条对齐**。
   所以这不是"从零做 3D"，而是"把已有的改活"。
3. **零预算 / 离线 / 一夜做完**三条硬约束，A 全满足（单 HTML、双击即开、不联网、不引任何 CDN）。

### 原版最大的短板（三个 agent 都指到了同一处）

原版 `elevator_3d_preview.html` 里的轿厢是 **`setInterval(2400ms)` 自己来回跳的**，
**和真实的呼梯、判层毫无关系**。对方只要问一句"这是真数据还是动画"，答不上来就废了。
——**所以本次的核心改动就是：让 3D 由"呼梯动作"驱动，并且把数据来源如实标出来。**

## 1. 三个方案对比

|  | 方案 A（GLM-5.3） | 方案 B（DeepSeek Pro） | 方案 C（本 agent） |
|---|---|---|---|
| 主展示 | 复制现有引擎 → **控制链数字孪生页** | 同一页，**接真数据**（`/api/status` 或 Web 蓝牙）+ 标来源 | **同一页**，并把"机构"也画进去 |
| 加分项 | 机构逐帧动画 MP4 + 9 张渲染图进 PPT | 3D 页面截图合成 MP4 插 PPT | 用真值尺寸画**机构剖视小窗**（动画） |
| 备用 | App 真机录屏 + 现有 9 图 | `?auto=1` 纯自演 + 9 图 | 现有 9 图 + 实物 |
| 最大风险 | STL 摆位（打印姿态≠装配坐标） | 真数据接不上（IP 变 / 蓝牙被拦） | 页面范围蔓延 |
| 不同意 | 反对把打印实物当主展示、反对 Three.js 重写 | 反对重写 3D（三端几何会漂移）、反对硬接真数据 | 反对只做静图 |

**三份方案在两件事上完全一致**（这也是最终拍板的依据）：
1. **主展示 = 现有网页 3D 引擎的延伸**，**绝不用 Three.js 重写** ——
   重写就意味着安卓 / 网页 / 文档三边的几何开始漂移，是这个项目最容易被抓的破绽。
2. **顺序铁律：先能演 → 再求真。** `SHAFT_MODEL.md` §0 自己就写了硬性要求：
   **测不到就标出来**。硬接真数据把演示搞崩，比老实说"这是模拟的"扣分多得多。

### 2.1 主展示页 `elevator_3d_model.html` 具体做了什么

**一句话：点一次 ▲/▼，把整条链在一个画面里演完。**

1. **控制链条**：`手机 App ▸ BLE 写入 ▸ ESP32 ▸ 舵机转 22° ▸ 按钮后移 3mm ▸ 轿厢过来`，
   呼梯时**按顺序逐个点亮**，对方一眼就知道"这一下经过了哪几道"。
2. **呼梯语义是真的**：只允许呼"你所在那一层"的按钮；**1F / 4F 点了会明确拒绝**
   （"没有呼梯装置"）——这是安全题的标准答法，写进界面里。
3. **回执是真话**：日志里写 `← 2F|OK:UP（= 舵机动作完成，不是"车动了"）`。
4. **机构剖视小窗**：尺寸**按真值**（曲柄 R=8mm、行程 = R·sinθ、22° → 3.00mm、销钉下垂 1.07mm、
   竖槽 13.6mm 吸收下垂），做成"左半按钮 / 右半机构 / 中间断开"的两段剖视，
   舵机动作时曲柄转、销钉在竖槽里滑、滑杆推着按钮后移。
5. **楼层判定用的是同一套算法**：中位窗口 3 · EMA 0.62 · 滞后 3dB · 连赢 1
   —— 和 App 的 `FloorJudge.kt` 完全一致，拖动"走廊位置"就能看判定怎么跟着变。
6. **数据来源角标**：默认写 **`数据来源：模拟`**；带上 `?api=http://手机IP:8899` 就轮询真接口，
   连上就改成 `接口（near）`，**连不上自动退回模拟且如实标注**——绝不留白屏。
7. **自动演示**：一个按钮进"走近 → 呼梯 → 到站开门 → 再走一层 → 再呼梯"的循环，**解放双手录屏**。
8. **不新增任何几何常量**：井道部分与原版、与安卓端逐字一致。

## 3. 为什么不做那三件事（明确记录，免得被反复问）

| 不做 | 为什么 |
|---|---|
| **不用 Three.js / WebGL 重写** | 现有引擎与安卓端数学同源、14 KB、离线单文件。重写 = **三端几何开始漂移**，这是最容易被抓的破绽。要加就加在同一个文件里。 |
| **不硬接真数据当唯一来源** | 手机 IP 会变、现场可能没网、Web 蓝牙可能被安全上下文拦。**降级路径必须是主路径**：默认模拟 + 如实标注，接口能连就自动升格。 |
| **不把 3D 打印件当主展示** | 打印件是**机构**不是"井道模型"，只有一层，讲不了轿厢运行。它做得很实（97.4 cm³ / 121 g / 全行程 0 干涉 / ±3.8mm 容差），所以**当加分的实物证据**放。 |
| **不为小参数重跑全量 CAD** | 全量构建 >120 秒，而且会覆盖已经出好的 9 张图。要改图就单跑那一张。 |

## 5. 风险与降级（现场用）

| 风险 | 触发条件 | 降级动作 |
|---|---|---|
| 真数据接不上 | 手机 IP 变了 / 现场没网 / 蓝牙被拦 | 什么都不用做：**页面默认就是"模拟 + 角标"**，照样演出完整条链；角标如实写"模拟" |
| 网页打不开 | 浏览器/显卡问题 | 用**原版** `elevator_3d_preview.html`（更简单）+ 9 张渲染图照讲 |
| 电脑完全不能用 | —— | `storyboard.html` 的 30 秒演出，或直接放**备用演示视频** `演示视频_备用.mp4` |
| 打印件没打完 | 时间不够 | 3D 页与视频都不依赖打印件；打印件只在"加分实物"那一拍出现 |

**一句话口径（现场照着说）**：
> "这是我们的 3D 控制链模型。**井道里那个轿厢是模拟的，页面上写着呢** ——
> 我们测不到轿厢真实位置，就不假装测到了。**但这三样是真的**：判层用的是 App 里同一套算法、
> 按钮被后拉 3.00 mm 是机构的真尺寸、呼梯只从你所在那一层发出去。"
