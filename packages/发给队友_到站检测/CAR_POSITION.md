# 电梯真实位置：到站检测（追加包 v1）

> 目标：把「轿厢现在在几楼」从**推测**变成**真数据**。
> 主资料包（`发给队友` v1.0）不做这个也**完全能演示**；做了之后，有人问「你怎么知道电梯在 3F」就有硬答案。
> 版本：**追加包 v1**（独立于主资料包，不随主包版本号变化）。
> 配套阅读：`SHAFT_MODEL.md` §0（为什么现有硬件测不出来）、§6（三种来源的取舍表）。

---

## 0. 问题，一句话

两块 ESP32 只会**按按钮**。回执 `2F|OK:UP` 的含义是「**舵机按压动作完成**」，**不是**「轿厢动了」。
电梯控制系统没有给我们任何反馈 —— 所以「轿厢在几楼」这个信息，硬件层面**根本没有出口**。

要把它是真的，只有一条路：**在外面再装一个传感器去"看/听"电梯自己**。

## 1. 四种来源对比

| 方案 | 真实性 | 成本 | 依赖 | 本项目状态 |
|---|---|---|---|---|
| **A. 推测动画** | ❌ 模拟 | 0 | 无 | 已可做。**UI 必须标"模拟"** |
| **B. 听电梯到站的"叮"声** | ✅ 真 | 一个麦克风模块（约 2~3 元/层） | 进厅能听见提示音 | ✅ **固件已写好**：`firmware/chime_node/`（编译通过，**未上机标定**） |
| **C. 光敏看呼梯按钮的灯** | ✅ 真 | 一个光敏电阻（约 2 元/层） | 舵机臂不挡视线 | ⬜ 未做 |
| **D. 摄像头读电梯自带的楼层显示** | ✅ 真（更细：给"几楼"，还知道"在动"） | 0（用手机摄像头） | 大厅有数字楼层显示、且数字够大 | ✅ **原型已写好并实测**：`preview/floor_display_reader.html` |

## 2. 方案 B 详解：听"叮"声（我们的固件）

### 2.1 硬件与接线（极简）

| 件 | 型号建议 | 说明 |
|---|---|---|
| 麦克风模块 | **MAX9814**（自带 AGC + 1.25V 偏置，最省事） | 备选 MAX4466 / 驻极体+LM386 |
| 电容 | 10~47 µF | 并在模块电源上，压纹波 |

```
模块 OUT  -> GPIO34     (ADC1_CH6，输入专用脚)
模块 VCC  -> 3V3
模块 GND  -> GND  （与 ESP32 共地）
```

ESP32 只在**本层**听：它听到"叮"就说明**轿厢到了本层** —— 这正好就是我们要的那一条信息。

### 2.2 判定原理（不用 FFT、不用库）

```
4 kHz 采样 → 每 40 ms 一个窗口 → 算 ①RMS(多大声) ②过零率(≈主频)
电梯"叮"是 1~3 kHz 的短促纯音：
    ① RMS 突然冲到「本底噪声 × 3」以上
    ② 同时过零率落在 700~1900 Hz
   → 连续 2 个窗口都命中 才认，再加 3 秒不应期
```

说话声/脚步声通常①满足②不满足（频率低），或持续时间不对 → 基本不会误触发。
代码里 `RMS_ON_FLOOR_MULT / FREQ_LO_HZ` 两个宏就是给你现场调的。

> **为什么上限是 1900 而不是 5200？** 4 kHz 采样 → 奈奎斯特只有 2 kHz，
> **超过 2 kHz 的声音会被混叠**。例如真实的 3 kHz "叮"会混叠成 1 kHz，仍落在带内 → **照样能报**；
> 所以上限写 1900（略低于奈奎斯特）就够，写 5200 是个无效值。
> （2026-10-17 修：早先版本只数了**上升沿**过零却用了"上下沿"的公式，频率被算小一半，
> 1200 Hz 的叮会读成 600 Hz、低于下限就永远不响。现在上下沿都数，实测 1200 Hz 读回 1200 Hz。）

### 2.3 现场标定（**这一步必须做**，代码里的只是保守初值）

**办法一（推荐，不用硬件）：用 `preview/chime_calib.html`**
（浏览器打开，给它麦克风权限）

- 它跑的是**和这个固件一模一样**的 DSP（4 kHz 采样 → 40 ms 窗口 → RMS + 过零率）；
- 先把手机/笔记本放到电梯厅，点"离线自测"确认逻辑正常，再开麦克风；
- 让电梯"叮"几下 → 每次都会进表（RMS / 主频 / 当时本底），右下角**直接给出可以粘回固件的 `#define` 那几行**；
- 它把麦克风也抽成 4 kHz（**不做抗混叠**，和固件一样），所以显示的频率就是**固件会看到的那个值**（可能已混叠），
  可以直接抄回去；页面上的频谱图是真实 48 kHz 视图，**2 kHz 以上固件看不到**。

**办法二（现场只能靠串口时）：**

1. 烧录 `firmware/chime_node/chime_node.ino`（`FLOOR_NAME` 改成 `"2F"`；另一块改成 `"3F"`）。
2. 串口 115200，站到电梯门口。每 2 秒会打印一行：
   ```
   [状态] 本底=12  最近 rms=14 freq=210Hz  已报0次  连接=0
   ```
3. **安静时**记下"本底"（通常 2~20）。
4. **让人在旁边正常说话** → 看 rms 涨到多少（通常 50~300）。**这时候不应该报警。**
5. 等电梯、听"叮" → 那一刻的 rms 会跳到 100~2000，并打印：
   ```
   [ding] 检测到到站提示音 #1  rms=780 freq=1850Hz 本底=12
   ```
6. 按第 3~5 步的数字调 `RMS_ON_FLOOR_MULT`：**安静/说话时绝不报，叮的时候必报**。
   若说话会误报 → 把 `FREQ_LO_HZ` 提到 900~1200。
7. 也可以让手机发 `LEVEL` 命令查实时数字（见下）。

> **诚实提醒**：不同大楼的电梯提示音差别很大（有的"叮"很轻、有的在轿厢内响而不是厅里、
> 有的根本没有提示音）。**上机标定之前，B 的可靠性是未知的**，不要当成一定能用。

### 2.4 协议（新增，不破坏已有约定）

设备名：**`CHIME-2F` / `CHIME-3F`**（**不是** `ELEV-2F`，所以两个节点互不干扰，可以同时连）。

Service / CMD / STATUS 三个 UUID 与按钮节点**完全相同**，所以手机侧连接代码可以直接复用。

**收到的报文（NOTIFY，形状与按钮节点一致：`<楼层>|<结果>`）：**

| 报文 | 含义 |
|---|---|
| `2F\|CAR:BOOT` | 节点刚上电，会开始听 |
| **`2F\|CAR:CHIME`** | **检测到"叮" → 轿厢到站 2F（这就是真数据）** |
| `2F\|CAR:LAST` | 回答 `FLOOR` 询问：最近一次到站是本层 |
| `2F\|READY:<n>` | 回答 `PING`：在线，并给出累计检测次数 |
| `2F\|LEVEL:rms=<v>,hz=<v>,floor=<v>` | 回答 `LEVEL`：现场标定用的实时数字 |
| `2F\|ERR:BADCMD` | 不认识的命令 |

**可以发的命令：** `PING` `?` `STATUS` / `FLOOR` / `LEVEL`

> 关键点：`CAR:CHIME` 和 `OK:UP` 是**两件事**，手机侧要分开处理：
> `OK:UP` = "我把按钮按下去了"；`CAR:CHIME` = "车到了"。**不要用 OK:UP 去推轿厢位置。**

## 3. 方案 D 详解：摄像头读电梯自带的楼层显示

原型：**`preview/floor_display_reader.html`**（三个模式：离线自测 / 现场照片 / 摄像头实时）。

不用通用 OCR（`VNRecognizeTextRequest` 对七段 LED 数码管非常不稳）。做法是纯几何：

```
灰度 → Otsu 阈值(自动判亮底/暗底) → 收紧包围盒 → 按长宽比归一化成栅格 → 角度搜索 ±10°
→ 逐像素 比对合成模板(10 数字 × 4 种数字格宽高比 × 5 种笔画粗细)的 L1 误差
→ 误差超门槛 or 与"次优的另一个数字"差距太小 → 输出"未识别"（绝不猜）
→ 实时模式：连续 3 帧一致才采纳
```

**实测（每档 150 个随机合成样本，难度 25/40/55/70）：**

| 模式 | 读对 | 读错 | 说明 |
|---|---|---|---|
| 「数字格」模式（推荐，AR/标定直接给框） | **84~89%** | **0~2%** | 其余为"未识别"。再叠加 3 帧一致，现场误读可忽略 |
| 自动找框（不标定时） | 80~89% | 0~5% | 窄的「1」容易被当成「0」（拉伸后宽度信息丢失）→ **所以推荐标定后给框，或者宁可"未识别"** |

**代价：** 数字高度需要 **≥ 20 px**。iPhone 15 Pro 用 ARKit 的
`ARSession.captureHighResolutionFrame()`（12 MP）在 2 m 处约有 **3 倍余量**。
普通 `capturedImage`（1920×1440，focal≈1300 px）在 2 m 处 4 cm 数字约 26 px —— 贴着 2 m 内可用。

## 4. 手机侧怎么用（iOS / 安卓同一套）

```
① 订阅 ELEV-2F / ELEV-3F（RSSI 定楼层 + 发 UP/DOWN）
② 订阅 CHIME-2F / CHIME-3F（听 CAR:CHIME）
③ 收到 xF|CAR:CHIME  → 轿厢目标层 = xF，来源标记 = "真数据"
   收不到 / 没装       → 用"约 1 层/2 秒"的模拟曲线，来源标记 = "模拟"
④ 井道里轿厢的位置条颜色：
   真数据 = 绿(或正常色)；模拟 = 加一枚"模拟"角标 + 稍微降低不透明度
```

**融合优先级（推荐写死）：**

```
听叮后的 CAR:CHIME（最新）  >  摄像头读到的楼层  >  模拟曲线
```

三者都要带**时间戳**：`CAR:CHIME` 超过 N 秒（建议 20~30 s）没更新，就退回下一级。

## 6. 边界与风险（别对外吹过）

- **B 未上机标定**。不同电梯的提示音差异极大；有的厅里根本听不到。**现场先试，不灵就退 A 并标注。**
- B 只能给"**到本层**"，给不出"现在在 3F 正在下来"。要中间态只能靠 D。
- C（光敏看按钮灯）可能被舵机臂挡住，未验证。
- D 需要**大厅真的有数字楼层显示**（本项目**还没实地确认过**：有的楼只有 ▲▼ 灯，没数字）。
  出门前先拍一张那张照片，确认数字 ≥ 20 px，再决定做不做 D。
- 所有"轿厢位置"只要不是来自 B/C/D，**UI 上必须有"模拟"标记**。这一条不能省。
