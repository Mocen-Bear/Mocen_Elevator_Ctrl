问题

电梯厅里的三件小事

① 手是满的

拎着东西、戴着厚手套、抱着孩子 —— 那个按钮就是按不到。

② 等得没道理

按完才发现车在 4F；黑箱里发生了什么，你完全不知道。

③ 井道是黑箱

墙后面有什么、车在哪、往哪走 —— 没有任何界面能告诉你。

我们只动“人伸手按按钮”这一件事，不碰电梯任何电气系统。

怎么做

四步，全部发生在你走向电梯的 3 秒里

① 靠近手机听 BLE 广播的 RSSI
不配对、不连接
→
② 判层哪些装置近？哪层
扫到信号立刻重判 · 节流 40 ms
→
③ 浮出右侧浮起“2F 上行”
点一下 / 说一句
→
④ 按下BLE 写命令 → 舵机压按钮
回执 2F|OK:UP

为什么判层要放在手机里

RSSI 是手机自己拿到的：不用连接就能判断，所以是“瞬时”的；
连接只在真正按下的那一刻建立。

为什么用舵机而不是改造电路

舵机按的是公共呼叫按钮，等于“有人伸手按了一下”。
不碰控制柜、不改线路，装置10 秒可拆。

  • 舵机真的把按钮按下去，回执可验证

真位置

“车在几楼”这件事，我们写了两条路

B · 听电梯到站的“叮”声

  • 一个麦克风模块（2~3 元）+ 4 kHz 采样
  • 40 ms 窗口算 RMS + 过零率，连续 2 窗命中 + 3 秒不应期
  • 报文形状与按钮节点完全相同：2F|CAR:CHIME
  • 固件已编译通过 ✓，标定台已就绪 ✓，待现场标定

D · 摄像头读电梯自己的楼层显示

  • 纯几何七段识别，不用通用 OCR
  • 单帧 84~89% 读对、0~2% 读错，其余输出“未识别”
  • 宁可说没看清，也绝不猜；实时要连续 3 帧一致
  • 需要数字高度 ≥ 20 px（现场照片确认）

两条路都没装的时候，界面上的轿厢位置一定带“模拟”标记 —— 这条不能省。

实测数字

“瞬时”和“不抖”，我们是拿数字说的

场景（20 s）朴素做法：谁强算谁我们的算法换现场参数后
站在某一层装置旁1 次1 次（只有首次上线）1 次
站在两层正中间（最坏位置）25.7 次横跳4.3 次1.3 次
从 2F 走到 3F（3 s 走完）1.9 s2.1 s2.5 s
  • 算法 = 中位窗口 3 · EMA 0.62 · 滞后 3 dB · 连赢 1 次 · 采样 200 ms（把 App 的逻辑逐行搬进网页跑仿真，6 个固定种子取平均，可复现）
  • 仿真故意按最保守的 200 ms 采样跑（真机上每扫到一次新信号就立刻重判、节流 40 ms，只会更快）；
  • “站在某层旁边”时判定在一个采样周期（200 ms）内出结果 → 这就是瞬时手感；
  • 换层慢不是算法慢，是几何上你得真的走近 —— 把滞后调大只多花 0.3 s，却把最坏位置的横跳压掉 19 倍。

怎么搭起来的

技术栈与分工

硬件 / 固件

  • ESP32 ×2（Arduino C++）
  • 舵机 ×2 + 外部 5V
  • 可加到站节点：MAX9814 麦克风
  • 自定义 BLE GATT 协议

Android App

  • Kotlin，自己写 BLE 管理（扫描 / 订阅 / 写队列）
  • 楼层判定：中位数 + EMA + 滞后 + 连胜
  • 本地 HTTP 接口（给队友 App 调，`/api/status` `/api/call`）
  • 软件 3D 渲染井道（无第三方 3D 引擎）

iOS / AR

  • ARKit + LiDAR 单层室内导航（队友）
  • 井道模型按规格文档对齐
  • 近距呼梯的悬浮按钮交互规格已交付

交付物是一整套：固件、App、协议文档、AR 规格、到站检测方案、演示手册与能力边界表。
